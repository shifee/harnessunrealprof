# Agent Execution Interface

The initial agent integration is transport-neutral and uses `unreal_harness.FileExecutionTransport`.

```python
from unreal_harness import FileExecutionTransport

transport = FileExecutionTransport("/path/to/project")
result = transport.submit({
    "format_version": "1.0",
    "dry_run": True,
    "commands": [{
        "id": "capabilities",
        "action": "system.capabilities",
        "arguments": {},
    }],
})
```

`submit` writes a complete document atomically to `Content/Python/actions.json`, waits for a new `result.json` with the same generated `run_id`, and returns the parsed result envelope. It never interprets Unreal actions or executes code itself.

## Machine-readable action contract

The source of argument schemas, mutation metadata and pure recipe expansion is `unreal_harness/action_contract.py`. The installer copies this exact module to `Content/Python/action_contract.py`; both host and UE executor use it. `ACTION_HANDLERS` remains the dispatch registry, and tests compare its keys with the contract. `system.describe_actions` publishes the schemas and examples. `docs/action-contract.json` is generated by `scripts/export_action_contract.py` (`--check` detects drift).

Validation covers required and unknown fields, primitive types and ranges, Blueprint operations and graph node kinds, dependencies, references and recipe expansion before mutations. Reflected metadata, class compatibility, asset existence and graph connections are still engine-side responsibilities. Resolved reference arguments are revalidated before opening the command transaction.

`AgentRun` executes read-only plans after dry-run; dry-run alone never counts as inspection. Common mutations receive read-back checks. Missing verification coverage or value mismatches produce `success: false`, `execution_succeeded: true` and explicit `verification_errors`, preserving the execution result. Explicit caller verification must be nonempty and read-only. No generic verifier can prove arbitrary user intent; callers must supply relevant checks for unsupported domains.

The transport preserves each submission/result pair in `Saved/HarnessAudit`. Batch failures block subsequent mutations and saves; successful earlier commands can leave partial changes, reported in the audit. Atomic file writes and per-command Undo transactions do not guarantee rollback of an entire batch or already persisted assets.

`FileExecutionTransport.session()` reserves the project mailbox with an OS file lock. `AgentRun` holds this reservation across planning, execution and verification. Concurrent callers fail before publishing a request. A timed-out submission retains `Content/Python/harness.pending.json`, so later callers cannot overwrite an unacknowledged request. A matching late response is archived before allowing another submission. On Editor startup the watcher resumes only unacknowledged reads and dry-run requests; uncertain mutations require review and are not replayed automatically.

Transport failures during verification preserve the execution result and its audit path. Verification checks final values after repeated Blueprint component edits and Material Instance parameter updates. Skipped verification commands cannot produce overall success.

The CLI runs local project/runtime/pending preflight before `ask`. `doctor --offline` performs these checks without contacting either service or writing the mailbox. Live `doctor` additionally submits read-only capabilities and discovers server model IDs through GET `/models`. This model check does not test inference. `models` lists IDs without an Unreal project. Both commands support `--json`. `ask --llm-timeout` sets a separate per-request inference timeout; `--timeout` remains the Unreal response timeout. JSON mode also emits valid JSON for configuration and transport errors.

## Agent loop contract

The default CLI `ask` now uses `TaskAgent`; `AgentRun` remains available through `--single-pass`. The loop follows this order:

1. Discover exactly one `.uproject` and confirm the target project root.
2. Query `system.capabilities` and `system.describe_actions`.
3. Inspect relevant state before proposing a mutation.
4. Freeze executable acceptance criteria derived from the original task and research observations, before any mutation.
5. Select a batch of at most 20 commands; validate and submit it as dry-run, then execute it.
6. Feed observations and known runtime errors back to the model. A runtime failure forces a read-only reconciliation step; unknown execution status stops the task.
7. On a finish proposal, run all fixed criteria. Failed predicates return to the loop. Report success only if all criteria pass.

The default limits are 8 model steps, 80 submitted commands including dry-run and acceptance, and 300 seconds. Host checks enforce the limits; network timeouts are capped by remaining task time. Identical mutations cannot be repeated across steps. References are scoped to each batch. `prepare_task` and `next_step` are the provider interfaces; step statuses are `act`, `finish`, and `unsupported`.

Criteria operators are `equals` (object subset comparison), `contains` (a matching list item), `exists` (a non-null field), `gte`, and `lte`. Paths select fields within command `data` using dots and numeric array indices; an empty path selects all data. Criteria are unconditional read-only commands and cannot reference another result. Model-authored criteria do not prove complete understanding of user intent.

`Saved/HarnessTasks` contains a single correlated task trace, including raw model requests/responses and Unreal observations, without API headers or keys. New traces are versioned, project-bound checkpoints for explicit continuation; legacy traces without a schema version cannot be resumed. `scripts/run_agent_evals.py` evaluates actual prompts against independent golden predicates in `evals/agent-tasks.json`; `--validate-only` checks suite structure without claiming native task success. Live trials use isolated asset namespaces and report semantic pass rate.

The loop MUST NOT bypass the executor with direct `.uasset`/`.umap` editing, arbitrary Python, shell commands, or concurrent submissions.

## Current transport limitation

The file watcher requires an open Unreal Editor with the installed Python harness. A missing or stale result times out with `UnrealExecutionError`; this is an infrastructure failure, not a successful empty result. Native UE MCP can be added later behind the same interface, but calls remain serial and the JSON result envelope remains the audit contract.

Transport validates every document before writing it. `result.json` is the complete audit record; the returned host result also contains its absolute `audit_path`.

## Task sessions and recovery

`tasks --project PROJECT` lists local checkpoints; `--task-id ID` returns a full checkpoint. These commands need neither Unreal nor model connectivity and do not submit commands. IDs are bounded to 32 lowercase hexadecimal characters and project identity must match.

`resume ID --project PROJECT` continues an unfinished task with its original criteria, read-only mode and explicit verification. It creates a new attempt with a parent ID and fresh budgets. Original traces remain intact. Fresh read-only reconciliation precedes further actions, and identical mutations from earlier attempts are blocked. Completed tasks require a new request.

`ask TASK --session ID --project PROJECT` supplies prior task context to target discovery and preparation, then freezes new criteria for the new request. Prior commands are context and are never automatically replayed. `run.ps1` exposes `-ResumeTask` and `-Session`. Single-pass mode does not support these features.

Every Unreal request is persisted with its correlation ID before submission. Continuation resolves unanswered requests against `Content/Python/result.json` or `Saved/HarnessAudit`. Unknown outcomes block before model calls or new submissions, even if the pending marker has been manually removed. A confirmed late response is added to the new attempt history, followed by live reads. An unsuccessful recovery does not create a checkpoint that could bypass the unresolved parent. Recovery never repeats requests, including reads and dry-runs; the watcher retains its independent conservative restart rules.

## Lifecycle hooks

`ask` and `resume` accept `--hooks FILE` (`run.ps1 -Hooks FILE`). Configuration is explicit JSON `{version: 1, hooks: [...]}`. Entries have unique `name`, `event`, argv-array `command`, optional positive `timeout` (default 10, maximum 60 seconds), `actions` glob patterns and `mutating_only`. At most 32 entries are supported. Commands run sequentially without a shell, with the configuration directory as cwd; Windows helpers launch without a console window.

- `before_action`: once per validated submission batch, including dry-run, capabilities, research and verification. UTF-8 stdin contains the document and context. stdout must be `{allow: boolean, reason?: string}`. A denial, malformed output, nonzero exit or timeout stops before request publication; no uncertain request is recorded.
- `after_action`: after a validated, correlated Unreal response is recorded. It observes the document and result. Errors stop the task while preserving confirmed execution and partial changes.
- `on_error`: observational notification for failed native batches (`scope: batch`) and failed task reports (`scope: task`). Handler failures preserve the original error and are traced; batch notification failures do not prevent reconciliation.
- `on_task_complete`: observes the final attempt report on success or failure. Handler errors mark an otherwise verified task unsuccessful with `verification_succeeded: true` and preserve execution evidence. Notifications do not recursively trigger themselves.

Action filters match the same command when combined and are forbidden for terminal hooks. Non-before hooks may return no stdout or JSON. stdout is spooled and capped at 64 KiB for parsing; stderr diagnostics are bounded. Hook timeouts share the task deadline. Exhaustion prevents further helpers from launching. Timeouts kill the direct helper process; descendants must not be left running by handlers. API headers and model credentials are not passed in event payloads.

Checkpoint hook settings include argv entries and cwd. Resume restores them unless an explicit configuration replaces them. New session requests use their own selected configuration. Hooks are trusted local programs with user privileges, not sandboxed model tools. Model output cannot install hooks or replace command documents through a hook response. Results are `hook_result` trace events. Existing single-pass and deterministic CLI commands do not use these lifecycle hooks. Example configuration and handlers are in `examples/hooks.json` and `examples/hooks.py`.

## Runtime and release gates

Correlated responses must include a boolean envelope success, structured command results with unique IDs and boolean success, and string-list changed-object evidence. A successful real execution must include every submitted command result; dry-run and native validation failures may have no results. Malformed or unknown replies never clear pending markers. Pending and archived documents are published atomically. Timeout and polling configuration must be finite and positive.

Known engine versions other than 5.8 and known mismatching contract versions are rejected before planning. Older test/adapter capabilities without version fields remain compatible; actual installed executor publishes both. Model request failures are traced as `model_error`, and unexpected planner exceptions finalize stopped checkpoints. `tasks` labels unfinalized traces `unfinished`, without asserting that a process is still running.

`scripts/check_release.py` provides host gates with optional build, undefined-name lint, installed-project diagnostics, and native fixture acceptance. It never starts Editor or model services. `scripts/run_native_acceptance.py` tests the real watcher, executor, lifecycle hooks, resume and follow-up context using a declared fixture planner. Native fixtures are not inference evaluation. The actual-prompt suite remains `scripts/run_agent_evals.py`, requiring a user-provided running model endpoint. See `docs/RELEASE_READINESS.md` for verified scope.

## Interactive CLI

`chat` / `run.ps1 -Chat` reuses the same TaskAgent interface and project preflight for each prompt. After a persisted result the next prompt uses its task ID as session context. `/new`, `/tasks`, `/resume ID` and `/exit` manage context and saved work. Read-only chat rejects resuming a mutation-capable task. EOF/Ctrl+C at the prompt exit normally; interruption during execution exits with code 130 and preserves checkpoints/pending evidence, without asserting cancellation of Unreal work. Each task receives fresh budgets. JSON output and single-pass mode are not supported. The command only connects to a configured endpoint and never starts model services.
